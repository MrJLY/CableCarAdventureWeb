# 开发要点

## 1. 坐标系与设计分辨率

- 设计分辨率固定 **1280 × 720**（横屏 16:9）。所有布局、HUD、关卡数值都按这个尺寸写。
- 实际渲染时整个 `root` 容器按 `min(w/1280, h/720)` 等比缩放并居中，多出来的部分是黑边（用天空色填充）。
- **y 轴向下**（Pixi 默认）。所有"高低"描述都是：**y 越小越高**。
- 关卡沿 x 单向推进，`WORLD_LENGTH = 9000`，轨道 x 范围 `150 ~ 8810`。

## 2. 关卡与轨道（`src/levels.ts` + `src/world.ts`）

### 2.1 关卡数据

`LEVELS` 是三个关卡的数组，每关一份 `LevelDef`：

```ts
{ name, subtitle, lives, features[], loops[], obstacles[], zones[], swarm?, pickups }
```

- `features`：轨道特征段（决定关卡长度与形状）
- `loops`：椭圆环轨的 r1/r2，数组长度决定最多能有几个环
- `obstacles`：`[可用弧长比例, 类型, 种子]`
- `zones` / `swarm`：区域与蜂群，同样用可用弧长比例
- `lives`：本关初始生命（HUD 心数按此动态显示，最多 `MAX_LIVES = 5`）

改关卡只需要改这个文件，`World` / `Obstacles` / `Pickups` 都从 `LevelDef` 读取。

| 关卡 | 世界宽 | 总弧长 | 环 | 障碍 | 生命 |
| --- | --- | --- | --- | --- | --- |
| 第一关 · 缆车试车 | 5640 | 7237 | 2 | 4 | 5 |
| 第二关 · 山间往返 | 9000 | 11784 | 3 | 7 | 4 |
| 第三关 · 风暴线路 | 11160 | 14959 | 4 | 11 | 3 |

### 2.2 参数化方式

轮架不是"x 的函数"，而是沿 **弧长 s** 前进的：

```
Track.px / py / cum[]   // 折线采样点 + 累计弧长
Track.poseAt(s)         // 弧长 → 世界坐标（线性插值）
Track.yAtX(x)           // x → 该处轨道最低点（y 最大），供地形与摆放使用
Track.atFree(f)         // 可用弧长比例 → 弧长坐标（自动避开环轨）
Track.endX / total      // 轨道终点 x / 总弧长
Track.loops[]           // 每段环轨占用的弧长区间
```

**为什么必须这样**：环轨和水平折返会让 x 折返，用 `y = f(x)` 表达不了。

### 2.3 轨道编排（`features`）

轨道不是解析函数，而是手写的一串「特征段」，逐段拼接：

```ts
y(u) = y0 + amp * (cos(π·waves·u) - 1)
x(u) = x0 + w·u - (fold·w / 2π) * (1 - cos(2π·u))
```

- `waves` 奇数 → 单调的 S 形过渡（段末 `y = y0 - 2·amp`）
- `waves` 偶数 → 一个往返鼓包（段末 `y = y0`）
- `fold` 约 0.7 → x 中途放缓但不折返，形成平缓的横向 S 弯
- 两式在 `u = 0 / 1` 处 `dy/du = 0`、`dx/du = w`，**接缝切线连续**，不会出现尖角
- **`fold ≥ 1` 绝对不要用**：x 会折返并与自身交叉，画出一个"压扁的小环"，视觉上不成立（踩过坑）

关卡的 x 跨度 = `Σ features[].w`，所以加段就是加长度。

**改这一段必须重跑可通行性校验**（见第 10 节），因为障碍位置、岩丘高度都挂在轨道几何上。

### 2.4 环轨

- 环是**椭圆**（`loops[]` 里的 r1/r2），采样 96 段拼接。
- 插入条件：某段结束时 `y ∈ [338, 394]` 且与前一个环相距 ≥ 1400px，最多 `loops.length` 个。
- 约束（改参数时务必重算）：
  - 环顶 `y - 2·r2` 不能出屏
  - 环底处车厢底部 `y + CABIN_DROP` 不能擦地
- 车厢在环顶时吊绳会穿过环的下半弧——这是几何必然，视觉上按"绳子在缆线前面"处理即可。

### 2.5 关键派生常量

```ts
CABIN_DROP = PHYS.ropeLength + cabinCenterOffset + cabinRadius = 130 + 48 + 44 = 222
```

即"缆线到车厢碰撞圆最低点"的总落差。地形容差、岩丘高度、环轨位置都以它为基准，**改绳长或车厢尺寸必须同步重算关卡参数**。

## 3. 玩家（`src/entities.ts` · `Cabin`）

- 车厢**恒定垂直悬挂**，没有摆动/旋转。
- 控制只有两个：右键加速、左键减速；左键按到底会反向后退（`vs` 允许负值）。
- 速度模型（`grip`/`wind` 由区域传入）：
```ts
vs += accel*dt                 // 右键
vs -= brake*grip*dt            // 左键
vs += wind*dt                  // 风区
vs *= exp(-drag*grip*dt)       // 滑行阻尼
vs = clamp(vs, -maxSpeed, +maxSpeed)
```

- 轨道两端硬边界：`s = 0` 时反向速度归零，`s = total` 时正向速度归零。
- 碰撞判定点 = 车厢中心 `(x, pivotY + ropeLength + 48)`，半径 44。

## 4. 地形与岩丘

- `groundY(x)` = `baseGroundY(x)`（约 637~694）减去所有岩丘的余弦鼓包。
- 岩丘 `PEAKS`：8 个，宽度 90~170，**丘顶恒定低于该处的车厢底部 12~58px**。
  - 高度按 `[x-w, x+w]` 整段范围内 `Track.yAtX` 的**最大值**反推——折返段同一个 x 会有多趟轨道，只取中心点会算矮，实测曾出现 -10px 的穿模。
- 因为现在没有垂直控制手段，岩丘只能是"擦身而过"的压迫感，**不能再做成致命物**——否则整关不可通过。这是速度控制方案下的硬约束。
- 实测：车厢底到地面**全程最小余量 22px**，任何位置都不会被地形卡死。

## 5. 障碍系统（`src/hazards.ts`）

统一接口：`view`（Container）+ `cx`（中心 x，用于视野剔除）+ `update()` + `hits(x, y)`。

| 类型 | 机制 | 通过方式 |
| --- | --- | --- |
| 摆锤铁球 ×3 | 摆幅 1.18~1.32 rad、周期约 5s，球扫过走廊 | 卡摆动相位冲过 |
| 电弧闸门 ×2 | 3.2s 周期，通电 58% | 等断电 |
| 蒸汽喷口 ×2 | 待机 1.4s → 预警 0.6s → 喷发 1.0s | 预警结束前冲过 |
| 落石区 ×2 | 两列碎石按 1.35s 周期下落 | 看节奏冲过 |
| 蜂群追击 ×1 | 进入区域后以 470px/s 追来 | 加速甩开 560px 或出区 |
| 冰面段 | `grip = 0.3` | 提前刹车 |
| 顺风区 / 逆风区 | `wind = +300 / -320` | 提前调整速度 |
| 浓雾段 | 云团堆叠遮挡视线 | 减速试探 |

**放置方式**：全部按「**可用弧长**」的百分比定位，不是 x 坐标。可用弧长 = 总弧长挖掉每段环轨前后各 360px 后剩下的区间。这样改轨道形状或增删环轨时，障碍会自动重新分布，不会落进环里。

### 布局约束（新增障碍时遵守）

1. **不要在环轨段内**放障碍（`atFree` 已自动保证）。
2. **不要在浓雾段内**放机制型障碍（看不见 = 不公平），雾段只放纯视觉或宽间距障碍。
3. 相邻机制间距建议 ≥ 450px（约 0.9s @ 620px/s），否则连续判定会变成必死。当前三关最小间距 627~835px。
4. 摆放新障碍后，**必须重跑可通行性数值校验**（见第 10 节）。

### 可通行性参考值

- 摆锤：扫描一个摆动周期内的所有进入时机，安全窗口约 **83%**（620/480/340 px/s 下相近）。
- 经验阈值：单项障碍安全窗口 < 70% 就偏难，< 50% 基本过不去。

## 6. 道具系统（`src/pickups.ts`）

沿赛道随机撒道具（每关 6~9 个，见 `LevelDef.pickups`），位置同样按「可用弧长」比例取，避开环轨。

| 道具 | 效果 | 时长 |
| --- | --- | --- |
| 护盾（蓝） | 免疫伤害 + 车厢外圈光环 | 5s |
| 磁铁（红） | 金币吸取半径 62 → 170 | 6s |
| 加命（粉） | 立即 +1 生命，上限 3 | — |

- 抽取池 `POOL = ['shield', 'magnet', 'shield', 'life']`，护盾最常见、加命最稀有。
- 被动效果在 `Game` 里用两个倒计时字段管理，每帧传给 `Hud.updateEffects()` 显示在底部居中的图标 + 剩余进度条。
- 护盾同时写进 `Cabin.aura`，`Cabin.sync()` 里画出脉动光环，这样视觉和判定用的是同一个数值。
- 命中判定半径 50（略小于图标半径，手感上"贴到"才算吃到）。
- `Game.crash()` 里第一件事就是判断 `shieldTime > 0` 直接返回，护盾期间完全免伤。

> **为什么没有「冲刺/加速」道具**：实测 boost 把最高速从 620 抬到 899 后，摆锤可通过窗口不变（83%），
> 但前方可见反应时间从 1.36s 掉到 0.94s，冰面上刹停距离从 328px 涨到 629px。门槛没变、容错变差，
> 收益不划算，已移除。要加回去务必先跑一次 `scripts/` 里的通行性与制动距离校验。

## 7. 美术

- **全部由代码绘制**：`Graphics` → `renderer.generateTexture()` 烘焙成纹理后再用 `Sprite`。
- 原因：零外部资源、包体小、可直接上微信小游戏；后续换真美术只需替换 `art.ts` 里对应的纹理来源。
- 每张纹理都用 `bake(renderer, w, h, draw)` 并显式传 `region`，保证纹理尺寸与逻辑尺寸一致（否则锚点会错位）。
- 换图时的接口约定：`Art` 接口里的字段名即资源槽位，保持 `Texture` 类型不变即可。

## 8. 音效（`src/audio.ts`）

全部**程序化合成**，项目里没有一个音频文件：

- Web 端用 `AudioContext`，微信小游戏用 `wx.createWebAudioContext()`，两者都拿不到就静默降级（`failed` 标记，之后不再重试）
- 基础单元是 `blip(频率, 时长, 波形, 增益, 延迟, 滑音目标)` 和 `noise(时长, 增益, 低通截止)`，都做指数包络避免爆音
- 浏览器自动播放策略要求首次交互后才能出声，所以在 `Game.bindInput()` 里挂了 `pointerdown` / `keydown` 首次手势调用 `sfx.resume()`
- HUD 右上角有静音开关，`Sfx.setEnabled()` 直接把 master gain 置 0

| 事件 | 声音 |
| --- | --- |
| 吃金币 | 988Hz → 1319Hz 两声方波 |
| 撞障碍 | 低通白噪声 + 180Hz 锯齿滑到 55Hz |
| 吃道具 | 三音上行琶音，生命 784 / 磁铁 587 / 护盾 659 起始音不同 |
| 通关 | C-E-G-C 四音 |
| 生命耗尽 | G-E-C 三音下行 |

## 9. 微信小游戏

- `src/minigame.ts` **第一行必须是 `import '../minigame/adapter.js'`**。ESM 按声明顺序执行，适配层必须先于 pixi.js 的模块级代码（pixi 在模块加载时就会读 `window`/`document`/`navigator`）。
- 构建产物是**单文件 IIFE**（`vite.minigame.config.ts`），入口 `src/minigame.ts` → `dist-minigame/game.js`。
- 产物目录需要 `game.json` + `project.config.json`，由 `scripts/copy-minigame.mjs` 从 `minigame/` 拷贝。
- `minigame/project.config.json` 里 `appid` 目前是 `touristappid`，**发布前必须换成自己的**。
- 小游戏里用 `resolution = 1` 且渲染尺寸取 `windowWidth * dpr`；适配层让 `getBoundingClientRect()` 返回 CSS 尺寸，Pixi 的触点映射才能对上。
- 主包体积约 515KB（gzip 156KB），远低于 4MB 限制。

## 10. 验证手段

### 8.1 视觉验证（无浏览器交互）

```bash
npm run dev
"%ProgramFiles(x86)%\Microsoft\Edge\Application\msedge.exe" \
  --headless=new --use-angle=swiftshader --window-size=1280,720 \
  --virtual-time-budget=4000 --screenshot=shot.png http://localhost:5174/
```

注意两点：

- headless 下 rAF 帧数很少，**相机 lerp 来不及收敛**。想截远处画面，临时把 `SPAWN_X` 改到目标区域，并把初始 `state` 改成 `'playing'` + `hud.hideOverlay()`，截完记得改回来。
- 端口可能被别的项目占用，`npm run dev` 会自动顺延，先确认实际端口。

### 8.2 数值验证

关卡参数（岩丘高度、环轨位置、障碍节奏）不要靠手玩试，写一次性 `scripts/_xxx.mjs` 复制公式做扫描，跑完删掉。历史用过的检查项：

- 车厢底 vs 地面：沿 x 逐 2px 扫描求最小余量
- 摆锤可通行率：对周期内所有进入时机 + 多种车速做碰撞扫描
- 环轨尺寸：环顶是否出屏、环底是否擦地
- 障碍落点：打印每个障碍的 (x, y) 与相邻最小间距，确认没有扎堆、没有落进环轨

**每改一次 `PHYS.ropeLength` / `cabinCenterOffset` / `cabinRadius` / `FEATURES` / `baseGroundY`，以上都要重跑。**

## 11. 性能

- 障碍按 `|cx - cabinX| > 1600` 切换 `visible`，并在各自的 `update` 内早退，避免屏幕外重建矢量。
- 主循环用固定步长：`dt` 上限 0.05s，按 1/120s 细分，最多 3 步。
- 地形是单个覆盖 9000px 的 Graphics，三角形数固定，不每帧重建。
- 每帧重建矢量的只有：车厢吊绳、摆锤绳、闸门电弧、蒸汽气柱；数量都在个位数。
